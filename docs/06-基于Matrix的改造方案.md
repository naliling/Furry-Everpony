# 基于 Matrix 的实施改造方案

> 本文件推翻 [01-技术选型](01-技术选型.md) 与 [03-架构与互联](03-架构与互联.md) 中「自己实现协议层」的部分。
> 协议层改用 Matrix，需求清单不变，只是**换底座、留外壳**。

## 一、为什么换

原方案要从零实现：全限定 ID、Ed25519 消息签名、防重放、联邦握手、离线消息、已读回执、在线状态、媒体存储。这些是 IM 里最难、最容易出安全事故的部分，从零做至少三个月，而且做不过已经跑了十几年的实现。

Matrix 是唯一同时满足下面三条的开源项目：

1. **自托管**：一个人就能跑起一个 homeserver
2. **实例互联**：原生联邦，`@号码:实例域名` 天生就是我们要的 fqid
3. **Bot 生态**：appservice / maubot，Bot 是一等公民

所以新原则是：**协议层全部白嫖，我们只写 Matrix 表达不了的东西。**

## 二、三层结构

```
┌─────────────────────────────────────────────────────┐
│  表现层  FE Client（React + matrix-js-sdk）           │  我们写
│  QQ 式三栏 / 号码搜索 / 好友列表 / 申请中心 / Bot 向导  │
└───────────────┬─────────────────────────────────────┘
                │ Matrix Client-Server API（客户端直连 homeserver）
┌───────────────▼─────────────────────────────────────┐
│  协议层  Matrix Homeserver（tuwunel）                 │  白嫖
│  账号 / 登录 / 消息 / 离线 / 已读 / presence / 联邦    │
└───────────────┬─────────────────────────────────────┘
                │ appservice 推送 + admin API
┌───────────────▼─────────────────────────────────────┐
│  旁路层  FE Sidecar（Node + Fastify + SQLite）        │  我们写
│  号码池 / 好友关系 / Bot 归属与审批 / AI 网关 / 邮件    │
└─────────────────────────────────────────────────────┘
```

关键点：**消息不走 sidecar**。客户端直接用 matrix-js-sdk 连 homeserver，sidecar 只处理「Matrix 表达不了的关系语义」。这样 sidecar 很小，也不成为消息瓶颈。

## 三、责任边界

| 能力 | Matrix 直接给 | 我们在 sidecar 补 | 我们不做 |
|---|---|---|---|
| 账号注册登录 | ✅ 账号体系 | 号码格式校验、号码池、邮箱验证 | 密码存储（交给 Matrix） |
| 数字 ID | ✅ `@localpart:server` | localpart 强制 6–9 位数字 | — |
| 消息收发 | ✅ | — | — |
| 离线消息 | ✅ | — | — |
| 已读回执 | ✅ | — | — |
| 在线状态 | ✅ presence | — | — |
| 实例互联 | ✅ 联邦 | 跨实例好友关系 | 联邦协议本身 |
| 好友 | ❌ 没有这个概念 | 全部 | — |
| 加好友申请 | ❌ | 全部（Bot 卡片 + 审批） | — |
| 拉黑 | ⚠️ 只有 ignore | 关系语义 | — |
| Bot 账号 | ✅ appservice 批量注册 | 归属、审批、配额 | — |
| AI 对话 | ❌ | 全部（BYOK 网关） | — |
| 邮件通知 | ❌ | 全部 | — |
| 群聊 | ✅ | 群与好友的映射 | — |

## 四、数字 ID 怎么落地

Matrix 的 localpart 字符集是 `[a-z0-9._=-/]`，**纯数字合法**。所以：

```
用户选的号码：3632823490
Matrix 用户 ID：@3632823490:furry.example
界面上显示：3632823490
跨实例显示：3632823490（内部记录 @3632823490:furry.example）
```

这正是 [03-架构与互联](03-架构与互联.md) 里设计的 `fqid = 指纹.号码`，只是把「指纹」换成了「homeserver 域名」，而且这个映射是协议层强制的，不是我们自己约定的字符串拼接。

注册流程：

1. 客户端提交「号码 + 邮箱 + 密码」到 sidecar
2. sidecar 校验号码格式（6–9 位、不以 0 开头）与号码池唯一性
3. sidecar 用 homeserver 的 **shared secret registration**（或 admin API）创建用户，`localpart = 号码`
4. 创建成功后写号码池表
5. 客户端拿到 matrix-js-sdk 的 access token，直接连 homeserver

限制：**Matrix 用户 ID 创建后不可改**。号码就是永久身份，跟 QQ 号一样。这符合需求。

## 五、好友怎么落地

Matrix 没有好友。关系真相存在 sidecar，通知用 Bot 消息卡片。

### 5.1 单实例内

```
A 加 B
  → 客户端 POST /api/friends/request { to: "3951331639" }
  → sidecar 写 friend_requests 表（pending）
  → sidecar 用 @friendbot:域名 往 B 的 DM 房间发一张 m.room.message 卡片
      内容："3632823490 请求添加你为好友"
  → B 的客户端把这张卡片渲染成「好友申请」组件（不是普通消息）
  → B 点同意 → POST /api/friends/accept { id }
  → sidecar 写 friendships（双向）+ 通知 A
```

客户端需要两个东西：好友列表（sidecar API）和申请卡片（Matrix 消息里的自定义事件类型）。

推荐用自定义事件类型 `fe.friend_request`，而不是普通文本消息——这样 Element 等通用客户端会忽略它，只有我们的客户端能渲染。

### 5.2 跨实例

```
A@实例1 加 B@实例2
  → 实例1 的 sidecar 调 实例2 的 sidecar：
      POST https://实例2/api/fed/friend-request
      body: { from: "@3632823490:实例1", to: "@3951331639:实例2", sig: ... }
  → 签名用实例的 Ed25519 私钥，公钥通过 Matrix 的 federation key API 获取
```

**重点：实例公钥不用自己发明。** Matrix homeserver 已经有 ed25519 签名密钥，联邦协议已经在用它签名。sidecar 直接复用同一个密钥对（从 homeserver 配置读取），对端通过 `/_matrix/key/v2/server` 拿到公钥验签。

这样 [03-架构与互联](03-架构与互联.md) 里设计的 TOFU 握手、公钥指纹校验，全部由 Matrix 联邦协议承担，我们只签名自己的业务消息。

### 5.3 群聊

**Matrix 的 room 本来就是群聊**：私聊是 2 人 room，群聊是 N 人 room，同一套协议、同一套同步接口。所以群聊不需要重新发明消息层，我们要自己做的只有三件事——群号、群管理、Bot 入群。

**群号**

- 每个群一个 6–9 位纯数字，与个人号码池**共用同一个计数器**，避免撞号
- 映射关系：群号 → Matrix `room_id`（`!xxxxxxxx:实例域名`）
- 界面上只显示数字，内部一律用 `room_id`
- 同时给 room 设 alias `#群号:实例域名`，跨实例邀请时用得上

**跨实例群（QQ 做不到的部分）**

- Matrix 联邦天然支持：一个 room 里可以同时有实例1、实例2、实例3 的用户，消息互通
- 群创建者的 homeserver 只是"创建地"，不是"服务器"——创建者下线、甚至整个实例关停，群依然存在，成员照样能聊
- 这条是产品卖点，不是技术细节

**权限模型**

- 直接用 Matrix 的 `m.room.power_levels`：群主 PL 100 / 管理员 PL 50 / 成员 PL 0
- 禁言、踢人、解散全部走 Matrix 原生事件（`m.room.member`、`m.room.power_levels`），我们只做中文 UI 翻译
- 不自己发明权限体系，省一大堆状态同步的坑

**Bot 入群（双确认）**

- Bot 不能自己进群。必须 **群主或管理员邀请 + Bot 主人同意**，两方都点头才进去
- 理由：防止有人把别人的 Bot 拉进群刷屏、烧别人的 token
- 审批状态记在 sidecar 的 `bot_access` 表，不写进 Matrix 状态

**Bot 在群里的行为**

- 默认**只响应 @**（@号码 或 @昵称），不 @ 不发言
- 群主可单独配置：是否允许主动发言、是否响应关键词
- 每个成员可以单独静音某个 Bot（本地设置，不同步）

**群公告 / 群头像 / 成员列表**

- 群公告 → `m.room.topic`（或自定义 `fe.room_announcement`）
- 群头像 → `m.room.avatar`
- 成员列表 → Matrix 原生 room state，不另存一份

**排期**：v0.1 不做群聊（先把单聊和好友跑通），v0.2 与联邦一起做。

**风险**

- 群聊消息量是单聊的几十倍，Bot 的 token 消耗会暴涨 → 必须默认 @ 触发 + 每人每日限额
- 跨实例大群的成员列表可能很长，客户端要分页拉取
- 群里的 Bot 回复要限速，否则一个热闹的群能把主人的额度烧穿

### 5.4 离线消息与送达状态

Matrix 的投递模型天然解决"对方不在线"：

- 消息先写进**发送方** homeserver 的 room
- 同步接口 `/sync` 是基于 `since` token 的增量拉取，对方上线时一次拿到所有未读事件
- 不需要自己写"补发"逻辑，未读数、已读回执（`m.receipt`）都是原生事件

三种"不在线"必须分开看：

| 场景 | 结果 |
|---|---|
| 对方客户端关了，实例还在跑 | **完全正常**。消息已存到对方服务器，对方一开客户端全收到 |
| 对方整台电脑关机（实例下线） | 发送方服务器按指数退避重试联邦投递。几小时内恢复 → 补投成功 |
| 对方实例长期离线（超过重试窗口） | 可能投递失败。消息仍留在**发送方**服务器，对方收不到 |

**产品原则：永远不让用户看到"因为对方离线所以发不了"。** 发送永远成功，只有送达状态不同。

状态设计：

| 标记 | 含义 |
|---|---|
| `✓` | 已发送（写进本机服务器） |
| `✓✓` | 已送达（对方服务器确认收到联邦事务） |
| 已读 | 对方客户端上报 `m.receipt` |
| `!` | 可能未送达（对方实例离线超过 24 小时） |

**和 QQ 的差别**：QQ 的消息永远躺在腾讯的服务器上，所以不存在"对方服务器关机"这回事。我们这条是自托管的固有代价，v0.1 先接受，v0.3 再考虑可选的中继暂存。

**发送方自己下线呢？**

不会丢，只会延迟。流程是：

1. 客户端 `POST /send`，homeserver **同步写盘**后才返回 `200` → 客户端打 `✓`
2. 联邦投递是异步的，如果关机时还没推完，事件进**持久化的 retry 队列**（存在数据库里，不是内存）
3. 下次开机 homeserver 启动，retry 队列自动继续投递 → 对方收到

所以：**只要客户端显示了 `✓`，这条消息就一定写进了磁盘，关机不影响，下次开机自动补投。**

真正会丢的情况只有一种：**发送方的实例永久消失**（硬盘坏了、软件卸载了、数据目录删了）。这时消息只存在于那台机器的磁盘上，对方永远收不到——Matrix 没有"发送方服务器主动拉回消息"的机制。

一句话跟用户解释：**你的电脑就是你的邮局，你关门了邮局就关门，但信件还在柜子里，下次开门接着送。**

v0.3 如果要做"发完就关机也不怕"，只有一条路：可选的中继暂存（消息先抄送一份到公共中继，默认关闭）。这违背零中心依赖原则，所以不放进 v0.1/v0.2。

### 5.5 数据归属与"对方删了怎么办"

Matrix 里消息是**双方各存一份**：发送方服务器存一份，接收方服务器存一份。联邦只负责把事件推过去，推完之后两边各自保管。

四种"删除"必须分开看：

| 对方做的事 | 你这边的结果 |
|---|---|
| 删掉他自己客户端的聊天记录 | **无影响**。你服务器上的副本还在 |
| 删好友 | 好友关系解除，**聊天记录仍在**（room 不会因为删好友消失） |
| 注销账号 / 卸载实例 | 你服务器上的历史消息还在，对方显示为"已注销" |
| **撤回消息（redact）** | **双向生效**。事件同步到你服务器，内容被抹掉，只留"已撤回"标记 |

只有**撤回**是协议层面真正的"两边同时删"，而且只有发送者本人（或群管理员）能撤回。

**数据所有权原则**：每个服务器只对自己存的数据负责，没有中心服务器能删掉你手里的副本。

代价是也没有客服能帮你恢复——**备份是你自己的事**。这一条要在首次启动时明确告诉用户，不能含糊。

## 六、Bot 与 AI

### 6.1 Bot 是 Matrix 账号

用 **appservice** 注册。appservice 可以一次性注册任意多个 bot 用户，不需要邮箱验证，也不需要用户交互。

```
@bot3632823490_1:域名     ← 3632823490 创建的第 1 个 Bot
```

appservice 注册时指定 `namespaces.users` 正则（例如 `@bot.*`），homeserver 把匹配的注册请求全部交给 appservice 处理。

### 6.2 归属与审批

- `bot_owner(bot_mxid, owner_number)` 存在 sidecar
- 只有已注册的个人号能创建 Bot（API 层校验）
- 别人加 Bot → 走 5.1 的申请流程，但接收方是 Bot 主人而不是 Bot 本身
- 主人同意后，建立 `friendships(owner_number, 申请人)`，Bot 才接受这个人的消息

### 6.3 AI 接入

sidecar 起一个 appservice HTTP 端点，homeserver 把 Bot 的消息事务推过来。

```
收到事务 → 解析消息 → 查 bot_owner → 查主人配置的模型（BYOK）
  → 调 OpenAI 兼容 API（流式）
  → 用 appservice 的 ephemeral 接口把回复发回去
```

BYOK 配置存 sidecar 的 SQLite，密钥用 AES-256-GCM 加密（参考 ChatPony 的做法）。

Bot 间对话限制（默认关、双方主人开启、10 轮、每分钟 5 条）在 sidecar 的发送前检查里实现。

### 6.4 Bot 生态

Matrix 生态里现成能用的：maubot（插件式 Bot 框架，903 星）、matrix-nio、matrix-bot-sdk。我们的 Bot 和它们可以共存——都是普通 Matrix 账号。

## 七、客户端怎么选（需要拍板）

| | 方案 X：改 Element | 方案 Y：自写客户端 |
|---|---|---|
| 基础 | fork element-web | React + matrix-js-sdk 从零搭 |
| 省下的工作 | 消息列表、富文本、媒体、已读、重连、加密 | 无 |
| 代价 | **AGPL-3.0 传染**，改了必须开源；代码库巨大，改布局容易改崩 | 全部 UI 自己写，4–6 周 |
| QQ 式三栏 | 要拆它的布局层，且它的状态模型是 room-first，和好友语义打架 | 自由 |
| 许可证 | 必须 AGPL-3.0 | 自选（MIT / AGPL） |

**我的建议是方案 Y。** 理由：Element 的 UI 是给「房间 / 线程 / 加密」设计的，改成 QQ 式等于重写布局层；而它的状态层以 room 为中心，我们的好友、申请、Bot 归属都不是 room，硬塞进去会比重写更累。matrix-js-sdk 已经把最难的部分（同步、加密、媒体、重连）做完了，我们只写界面。

## 八、部署形态

单实例最小部署：

```
tuwunel（单二进制，Rust，SQLite 后端，监听 :8448 + :8008）
  ├── FE Sidecar（Node，:7788）
  └── FE Client（静态文件，由 sidecar 托管或单独 nginx）
```

- 内网/本机：直接 `http://127.0.0.1:8008`
- 公网联邦：需要域名 + TLS 证书 + 8448 端口可达，或走 `.well-known` 委派
- 不想开端口：Tailscale 组网（免费 100 设备），联邦走内网 IP

### 8.1 "服务器"到底指什么

用户听到"服务器"第一反应是要租机房。**不是。**

**homeserver 就是跑在你自己电脑上的一个程序。** 不需要买任何东西。

| 你想做到 | 需要什么 | 花钱吗 |
|---|---|---|
| 自己用、和几个朋友聊 | 你自己的电脑（现在这台就行） | 不花 |
| 朋友也用 | 他们各自下载安装包，跑在自己电脑上 | 不花 |
| 我关机了、别人还能给我发消息并送达 | 一台常开的机器：旧笔记本 / 树莓派 / 家里 NAS / VPS | 免费到几十元/月 |

开发阶段：跑在 WSL2 里，只监听 `127.0.0.1:8008`，本机访问，不暴露公网，也不需要暴露。

给别人用的两条路：

1. **Tailscale 组网**（推荐，免费 100 设备）：双方装 Tailscale，走内网 IP 联邦，不需要域名、不需要开端口、不需要备案
2. **公网域名**：需要域名 + TLS + 8008/8448 可达，家庭宽带通常还要内网穿透

**"我的服务器在哪"的答案是：在你电脑上。** 和你现在装的 QQ 客户端一样，只是它同时承担了腾讯那边的那部分工作。

## 九、风险

| 风险 | 影响 | 缓解 |
|---|---|---|
| tuwunel 太新（2026 年才接替 conduwuit） | 可能有未知 bug | 备选 Synapse（稳但重，要 Postgres + Python） |
| Matrix 联邦要域名 + TLS | 朋友加入门槛高 | 先做单实例，联邦放 v0.2 |
| Element 的 AGPL 传染 | 若走方案 X 必须开源 | 走方案 Y 可自选许可证 |
| 号码不可改 | 用户选错就没救 | 注册页二次确认 |
| homeserver 升级破坏兼容 | 断服 | 锁定版本，升级前看 changelog |

## 十、v0.1 验收（修订）

1. `docker compose up` 或 `start.bat` 起 tuwunel + sidecar + client
2. 用邮箱注册，自选 6–9 位号码，得到 `@号码:本地域名`
3. 搜索号码加好友，对方收到申请卡片，同意后出现在好友列表
4. 双方互发消息，离线能收到，已读回执正常
5. 创建 Bot，填自己的模型 key，Bot 能回复
6. 别人加 Bot 需要主人审批
7. 断开重连后消息不丢
